- C5: same loop-2 failure as C4, plus the changed loop-1 pointer copy.
- C6: hoists the r7 literal load ahead of state initialization and changes literal-pool ordering; loop 2 still uses r7 as its pointer.
- The phase pseudo is **48** in C1-C5, **29** in C6. All retain `pref LO_REGS`; none gains `STACK_REG` preference or ends up in ip.
- C1 pseudo 48 conflicts include r0-r6 and r8, but **not r7**. C4 likewise lists `0 1 2 3 4 5 6 8 13`, leaving r7 available. The longer lifetime therefore does not create the missing conflict that would force a high register.
- C4 reports a spill of r7 elsewhere, but its loop-2 phase pointer remains r7 in final assembly. A spill message alone is not evidence of the desired eviction into ip.

These results reject the tested source forms, not every possible source expressing either hypothesis. Further progress needs a different conflict/reload mechanism; repeating ordinary pointer lifetime changes alone has no supporting result here.

### 1. Actual loop-2 liveness and overlapping pseudos

C4 is the useful ordinary-pointer example. Pseudo **48** is defined by insn **112**, copying hard r3 immediately after the update. It is live into setup BB8 and around the BB9 loop backedge, then dead on exit. Its value is needed again in the next iteration, so it remains live after its byte load. BB9's `.lreg` entry set is:

```text
1 2 3 4 5 7 8 13 48
```

Here hard r7 is also the compiler's eliminable frame-pointer reference; its appearance in this entry set is not evidence of a competing allocated C value.

The overlapping ordinary loop-2 pseudos are exactly those named in the conflict row:

```text
;; 48 conflicts: 48 77 79 82 83 0 1 2 3 4 5 6 8 13
```

| C4 pseudo | Defining/consuming insns in `.lreg` | Value | Local allocation |
|---|---|---|---|
| 77 | 215 -> 217 | scroll halfword plus loop index | r0 |
| 79 | 224 -> 230 | ripple-table address | r0 |
| 82 | 230 -> 231 | signed ripple-table byte | r0 |
| 83 | 231 -> 234 | ripple value plus source halfword | r0 |

All four are block-local in BB9, prefer LO_REGS, and are explicitly assigned r0 in the `.lreg` allocation listing. They reuse r0 at separate points; they do not require four simultaneous registers. Their conflicts with phase 48 are genuine, but after local allocation they contribute r0 interference, not r7 interference.

Other already-required values are hard-register RTL: r1 is the index, r2 the source pointer, r3 the destination pointer, r4 the ripple-table base, r5 the mask, and r8 the scroll base. Hard r6 is the scroll-address copy in insn 202 and dies at insn 207's halfword load. There is **no phase-byte pseudo** at this stage: insn 217 has a QI memory operand inside the add. Likewise, insn 231 contains the source HI memory operand inside its add; it is not a separately live source-value pseudo.

The loop-1 pseudos 54 and 58 are global but do not overlap phase 48 in C4's liveness: phase is dead along that successor. Their assignment to r1/r2 cannot displace phase in loop 2. Initial state/table-setup pseudos are also dead before phase's loop-2 lifetime.

### 2. Why r7 is absent: an explicit allocator rule

This is stronger evidence than the final assembly. In `global.c:483-495`, after `global_conflicts()` and **before allocation**, agbcc removes conflicts and copy preferences involving every eliminable register:

```c
AND_COMPL_HARD_REG_SET (hard_reg_conflicts[i], eliminable_regset);
```

`thumb.h:581,589-592` defines r7 as FRAME_POINTER_REGNUM and includes r7 -> sp in ELIMINABLE_REGS. Thus merely extending a hard-r7 use cannot be assumed to add a durable global conflict. This also explains why the `.lreg` live set can contain r7 while the printed global conflict row omits it, and provides a source-level explanation for the earlier explicit-r7-pin miscompile. No such pin was attempted here.

There is a distinct route: **another globally allocated pseudo** could receive r7 first. `global.c:1212-1220` propagates that assignment into the hard conflict sets of conflicting pseudos **after** the initial eliminable-register clearing. That interference would be real. None of C4's four loop-2 temporaries supplies it: they have already received r0 locally. `local-alloc.c:1907-1917` explicitly excludes eliminable registers, so making another ordinary block-local temporary cannot make local allocation choose r7.

### 3. Actual reload reservations and inserted instructions

The C4 `.greg` messages and resulting RTL distinguish reservation from actual pseudo eviction:

| Original insn | Reason | Recorded reservation / emitted reload |
|---|---|---|
| 106 | phase update's memory add operand | reserves r1; inserted insn 271 loads state byte into r1 |
| 143 | loop-1 phase byte operand | reserves r7; inserted insn 274 loads phase byte into r7 |
| 185 | literal load into hard r8 | reserves r0; inserted insn 277 loads the scroll address into r0 before copying to r8 |
| 217 | loop-2 phase byte operand | reserves r6; inserted insn 280 is `QI r6 = mem[phase r7]` |
| 231 | loop-2 source halfword operand | reserves r6; inserted insn 283 is `HI r6 = mem[src r2]` |

The loop-2 `r6 = r8` is **original insn 202**, already present before reload. In these sources it is not a reload event and cannot be used as evidence for the supposed preceding round-robin choice of r6. This corrects a premise in the earlier report's proposed target explanation. The target could have a different RTL origin, but the baseline/C4 origin is established by the dumps.

`new_spill_reg` (`reload1.c:2130-2177`) prints “Spilling reg” when reserving a hard register for that instruction. This does not by itself prove any pseudo was evicted. `find_reload_regs` only marks a pseudo for eviction when it occupies a reserved register and is live before or after that particular instruction (`reload1.c:1867-1885`). The loop-1 r7 reservation therefore does not evict C4 phase 48: phase is dead there. At the setup/loop-2 reservations it is live, but they reserve r0 or r6, not r7.

The cost policy explains that choice without guessing from assembly. `order_regs_for_reload` (`reload1.c:3766-3847`) excludes live explicit hard registers, counts references of live allocated pseudos, and prefers available registers with no occupying pseudo. At insn 217, r6 is dead after the scroll load and is available at zero occupancy cost; r7 holds phase 48. At 231, r6 is also available. Both are single scalar memory operands; no second simultaneous low-register reload is required. The patterns examined have no mandatory hard-r7 operand.

Baseline provides a useful contrast. Its ip pointer is explicit hard r12, and `.lreg` already contains address-copy pseudo **77**, locally allocated to r6. Its loop-2 load writes the explicitly bound hard r7. The wrong `mov r6, ip` therefore originates before reload; there is no evidence that changing reload rotation alone can fix this baseline. C4 removes that expand-time address copy by using an ordinary pointer, but then allocates the pointer itself to r7.

### 4. Could an existing lifetime/expression force eviction without extra instructions?

There are two theoretically relevant constraints, neither supplied by the saved sources:

1. An overlapping **global** pseudo allocated to r7 before phase, as described above. An already-local temporary would need a real cross-block/cross-iteration lifetime to enter this route. All the arithmetic-result lifetimes in the table end inside BB9; their values are recomputed independently in the next iteration. Merely naming them differently does not establish that lifetime. Keeping an old iteration's result needed would change the computation, require another use, or be removed if dead. Earlier shared-value experiments were already split by optimization; they were not repeated.
2. A required reload at which r6 is unavailable, or at least two independent low-register reload needs when r6 is the only free low register. Phase could then be evicted from r7. Current loop-2 adds need only one memory-operand reload each. Keeping a source value in r6 across the phase load requires an earlier source load, whereas the target loads it **after** the signed table lookup. Keeping the scroll-copy value alive later requires a real later use that the target does not have. Earlier source-load-order experiments also failed to retain the intended order. No new source expression was identified that changes these constraints while retaining the target instructions.

This is not a proof that no C expression can work. It is a reason to stop here rather than compile speculative lifetime rewrites. No already-required instruction was found that intrinsically demands r7 while phase is live.

### 5. Would genuine interference/eviction plausibly select ip?

**Plausibly, but not automatically.** `global.c:926-1017` first tries the preferred class, then the alternate class if needed (`global.c:574-582`). `retry_global_alloc` does the same at lines 1232-1258. `finish_spills` (`reload1.c:3508-3599`) can evict a pseudo, forbid its previous home plus registers reserved while it is live, and retry allocation. This is whole-pseudo reallocation, not simply saving r7 temporarily to ip at the one instruction.

If r0-r7 are unavailable and the alternate class permits high registers, ip is a sensible outcome: the first search pass favors registers already used or call-clobbered; ip is call-clobbered, r8 already conflicts, and unused callee-saved r9/r10 would require new saves. r11 is fixed in this configuration. However, these dumps report preferred class, **not alternate class or a complete allocation-attempt trace**. They do not establish that phase 48's alternate class admits ip. `regclass.c:1011-1075` computes the alternate class from costs versus memory. Consequently, “one more conflict guarantees r12” would overstate the evidence.

There is also a correction to the earlier reports: in the inspected `thumb.h:428-469`, **STACK_REG is only sp** (mask `0x02000`), **HI_REGS** is the high-register class (mask `0x0ff00`), and LO_REGS is `0x000ff`. The earlier claim that STACK_REG means high registers is incorrect for this source. Any historical Catbat dump described as STACK_REG needs separate verification against its actual compiler configuration; it is not a sound premise for this function. No Catbat experiment was performed here.

### 6. Other possible origins of the target copies

The target's `mov ip, r3` alone does **not** identify its allocation mechanism. The verified baseline already produces this instruction from an explicit hard-r12 assignment. Other possible origins are a normal global pseudo assigned ip initially, or a pseudo moved there by reload's global-allocation retry. The ordinary-pointer/eviction explanation remains a hypothesis, not an established fact about the original source.

Likewise, the target's `mov r7, ip; ldrb r7, [r7]` need not prove that its byte and address are both reloads. It could involve a globally allocated low address/value pseudo, or post-reload optimization of a different RTL form. What is established is narrower: the saved baseline's block-local address-copy pseudo cannot get r7 through local allocation. `toplev.c:3094-3147` also runs `reload_cse_regs` and later jump optimization after allocation; `.greg` therefore is not a pristine trace of every intermediate allocation choice. Final assembly cannot distinguish these origins.

No concrete C source was found that gives such an alternative origin while preserving the required loop and initialization instructions. These alternatives are recorded as limits on the earlier inference, not candidate proposals.
